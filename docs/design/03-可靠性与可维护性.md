# 开发版本一：软件可靠性与可维护性的实现

> **这份文档回答一个问题**：这套系统（Go 后端 + React 管理端，AR 手机端待做）要满足什么，
> 才算"可靠、可维护"。
>
> 它**不写实现**，只写逻辑与作用——实现落在代码里，验收对着第 5 节的清单逐条结算。
>
> 对应 ISO/IEC 9126（中国国标 GB/T 16260）六特性中的两项：可靠性、可维护性。
> 其余四项（功能性、易用性、效率、可移植性）的现状与缺口另文记录。
> 备注：该模型后续被 ISO/IEC 25010 取代（2011 版 8 项、2023 版 9 项）；本项目以 9126 六项为框架，
> 但额外把"可观测性"算进来——它不是 ISO 指标，却是生产环境出事时排障的前提。

---

## 1. 可靠性：三个不同的问题，别混成一个

"可靠"在日常语言里是"别出错"，但在工程上是三件事，它们的手段完全不同。

### 1.1 少犯病（成熟性）——降低出错概率

**逻辑**：错误的总量 ≈ 场景数 × 每个场景的出错率。所以要么减少场景数（把入口收窄），
要么压低单点出错率（穷举边界）。

**作用**：把"随机故障"变成"概率低到可以不谈"。

对这套系统，最常见的"病"不是逻辑写错，而是**两端对同一份契约的理解不一致**——
这是代码本身正确、但整体出错，最典型的一种。所以降低出错率的第一手段不是"写得更小心"，
而是让三方只有一份定义、并且定义一旦漂了能被立刻发现。

### 1.2 犯了病不崩（容错性）——限制失败的传播半径

**逻辑**：一次失败会影响多大面？这个问题必须**在设计时回答**，而不是等出事时看运气。

- 前端的错误分流就是这个道理：字段错显示在那一行（用户改一下就好），记录不存在升到页面级
  （要刷新），服务挂了升到顶部横幅（重试也没用）。三种失败，三个半径。
- 后端同理：参数校验挡住脏数据进库、统一错误出口保证客户端永远拿到同一种形状、
  内部错误只回一句人话而把 SQL 细节留在日志里。这些都是"失败被关在笼子里"。

**作用**：把"局部错误"和"整体不可用"隔开。

一条记录有问题不该让整个列表白屏——这正是为什么 v1 选择"一条坏记录报错整页"，
而当数据量到几百条时，这个选择要改成"坏的进日志、好的照常显示"。

### 1.3 崩了能回（易恢复性）——缩短停机与恢复完整

**逻辑**：MTTR = 发现时间 + 定位时间 + 修复时间 + 恢复数据的时间。
可靠性工程真正能压缩的是后三项。

后端：优雅退出（把在飞的请求放完）、WAL、重启后数据仍在、幂等（重复提交不产生第二条记录）
——全是"恢复时不用做额外判断"。
前端："每次进页面都重拉、不本地缓存"也是同一类：关闭浏览器即清空，恢复就是重新 GET 一次，
没有"过期缓存要手动清"这种恢复步骤。

**作用**：把事故从"要处理"降级为"刷新一下"。

### 1.4 核心洞察：敌人不是出错，是"沉默的出错"

返回 200 但字段缺了、界面显示了数据库里没有的状态、写了但没落盘——这些都不响，比报错危险得多。

所以可靠性在设计上可以浓缩成一句话：**每个失败都必须可见，并且被关在最小的范围里。**

这条对前后端同时成立。前端不是"受害者"，它是链条的一环——不做乐观更新、不缓存、
按错误码分流，本身就是可靠性设计。

## 2. 可维护性：四个问题，衡量的是"下次理解它的成本"

### 2.1 能不能定位（易分析）

**逻辑**：从"用户说不对劲"到"知道是哪个位置"，中间要经过几次猜测？每一次猜测都是成本。

**作用**：把排障从"猜"变成"查"。

现状已有一个真实案例：前端请求日志与后端每请求日志，两边时间戳一对，就能判断卡在浏览器、
网络还是后端。缺的不是日志，是**两边没有共同的标识**——时间戳对账在并发时会失效。

### 2.2 改得动吗（易改变）

**逻辑**：一次业务改动的**变更半径**有多大？改一条状态规则要动几个文件？

**作用**：需求变化时不至于连锁修改。

这里有个必须承认的现状：契约在三端各翻译一次（Go 结构体、TS 类型、未来 C# DTO）。
这不是设计失误，是跨语言系统的必然成本——所以能不能维护，取决于**有没有纪律保证三处同步**，
而不是取决于能不能消灭这三处。

### 2.3 改完会不会炸别处（稳定性）

**逻辑**：有没有办法在"改"的当下知道"别的没坏"？

**作用**：把"敢改"变成日常。

这就是自动化测试与 CI 的全部意义——不是为了分数，而是为了让**改动变得便宜**。
没有它，改一处要人工把所有场景点一遍，成本高到人会选择不改，于是代码开始腐烂。

### 2.4 测得动吗（易测试）

**逻辑**：一处逻辑"能不能被单独验证"？

**作用**：测试的成本决定测试是否存在。写不动的测试等于没有测试。

这也是分层的一个实际收益：`model` 是纯函数、不碰 IO，所以 13 项单测半小时写完；
handler 要连数据库，测起来贵，于是一直拖着没写。

**结构决定测试成本，测试成本决定可维护性**——顺序是反的：先有结构。

### 2.5 核心洞察：成本不在"写"，在"下次理解"

所以可验收的衡量方式不是"代码好不好看"，而是：

> **一个新人从 clone 到能安全改第一条规则，需要多久？**

文档、注释、契约、测试、CI，全都服务这一个数字。

## 3. 两者的交叉点只有一个，但它最划算

**可观测性。**

它是可靠性的"发现能力"（沉默的出错必须被看见）和可维护性的"定位能力"
（从症状到位置）的同一条基建。

所以顺序上应该最先投它——一次投入，两个指标同时涨。

---

## 4. 一个必须点出来的张力：可靠 vs 可维护

这两项在方法论上是有冲突的：

- **可靠性**偏好：少动、少抽象、少依赖、少分支
- **可维护性**偏好：分层、抽象、可替换、可测试

冲突时怎么裁？标准是**看变更频率和失败代价**：

| | 失败代价高 | 失败代价低 |
|---|---|---|
| **变更频率低** | 少抽象，写死，求稳（数据存储、契约） | 随便写 |
| **变更频率高** | 抽象，但要可测（状态机、错误处理） | 大胆抽象、快速迭代（界面文案、布局） |

所以"数据存储该不该上 ORM"这类问题的答案是**看它变不变**：我们的表基本不变，
就不该为它引入抽象层。这与"可维护性要求分层"并不矛盾——分层的目的从来不是层数多，
而是**让会变的地方独立于不变的地方**。

## 5. 落到这个产品：逻辑层的验收清单

不谈实现，只谈必须成立的事。后续每个改动都对着编号结算。

### 5.1 可靠性要满足 6 条

| # | 要求 | 说明 | 当前 |
|---|---|---|---|
| R1 | 每个失败有唯一形状、唯一归属 | 谁的错、谁能修，一眼能分 | ✅ 统一错误体（四个 code） |
| R2 | 失败不跨边界传播 | 一个字段错 ≠ 整页不可用 | ✅ 错误按 code 分流：行内 / 顶部 / 重试 |
| R3 | 重复操作不产生副作用 | 手快点两次，不多一条记录、不留假时间戳 | ✅ 同状态 PATCH 幂等且不刷新 `updatedAt` |
| R4 | 状态只有一个真源，界面不自行编造 | 不做乐观更新、不跨会话缓存 | ✅ 前端等响应再更新；进页面就重拉 |
| R5 | 重启不丢数据，恢复无需额外步骤 | 进程挂了、重启，数据完整 | ✅ SQLite + 优雅退出 |
| R6 | **每次改动之后，R1–R5 仍然成立** | 把"手工验过"变成"每次改动都验" | ❌ **最大缺口**：后端有 34 项冒烟，前端 0 测试，无 CI |

### 5.2 可维护性要满足 5 条

| # | 要求 | 说明 | 当前 |
|---|---|---|---|
| M1 | 一份契约、明处翻译、同步有纪律 | 三端各翻译一次是必然成本，靠纪律同步 | ✅ `docs/api.md` 为唯一来源 + 冒烟验漂移 |
| M2 | 依赖单向、无环，方向由工具强制 | 不靠自觉 | ✅ `api → store → model`，Go 编译器把关 |
| M3 | 会变的逻辑独立于不变的表达 | 业务判断集中，渲染只管画 | ✅ `model` 纯函数 / `hooks` 承载状态机 / 组件只画 |
| M4 | 决定的**原因**被写下来 | 不只是"做了什么" | ✅ 代码注释 + README 已知缺口 + AI_LOG |
| M5 | 验证成本低到会被执行 | 低到"改完顺手就跑" | ⚠️ 部分：后端 `go test` 一行就跑；前端无测试可跑，也无 CI |

**结论**：可靠性的缺口集中在 R6，可维护性的缺口集中在 M5——**其实是同一件事：没有回归机制**。
这两处的投入（自动化验证 + 持续集成）同时抬升两项指标，是本阶段最高性价比的动作。

---

## 6. 怎么用这份文档

1. **当下**：第 5 节的两张表是验收标准。任何改动前先问"它让哪一条从 ❌ 变 ✅，或从 ✅ 变危险"。
2. **提分顺序**：先做可观测性（第 3 节）→ 再补回归机制（R6 / M5）→ 最后才谈抽象与分层。
   顺序反了，就会为了"看起来工程化"引入没人验证的层。
3. **不做清单**：鉴权、分页、作废状态、截图、历史表、离线队列、容器化部署，
   一律写进 README 的"已知缺口"，并在评审时主动说明——**把"不做"讲清楚，比塞半成品更加分**。
