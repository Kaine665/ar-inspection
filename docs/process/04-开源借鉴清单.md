# 开源借鉴清单

> 调研时间：2026-10-27　方法：GitHub Search API 多组关键词 + 官方仓库目录核对
> 立场：**只借鉴公开的、官方的、可复用的东西；不看他人的同题作答。**

## 一、开源调研结果

**没有现成的「Unity AR → Go → React」三端闭环可以借鉴。** 换了七八组关键词（AR 巡检、AR 标注、缺陷上报、anchor placement、CMMS），最接近的也只是单端 demo。这本身是个信号：**这道题没有可借鉴的现成代码，正因为没有才拿来考。**

但每一块零件都有成熟的东西：

| 件 | 来源 | 借什么 |
|---|---|---|
| **AR 放置逻辑** | [arfoundation-samples](https://github.com/Unity-Technologies/arfoundation-samples) ★3437（官方，46 个场景） | `SimpleAR` 场景就是「点平面放物体」，我们的核心动作照它写；`PlaneDetection` 抄平面可视化；`Markers` 是图像追踪，将来做跨会话定位加分项用得上 |
| **业务领域模型** | [Grashjs/cmms](https://github.com/Grashjs/cmms) ★845（自托管维护管理系统） | 不是抄代码，是拿它的工单字段对照我们的 BR-01～12，看有没有漏（比如 assignedTo / dueDate / closedBy） |
| **AR Foundation 源码** | [needle-mirror/com.unity.xr.arfoundation](https://github.com/needle-mirror/com.unity.xr.arfoundation) | 只在 debug 时查 |

**商业产品**（Scope AR、Vuforia Chalk、Taqtile Manifest、亮风台 HiAR）可以看的只有交互套路，而且它们的做法跟我们 BR-05 的结论一致：**交接靠截图 + 文字，不靠坐标。**

## 二、⚠️ 三个疑似同题仓库——明确不采用

GitHub 上搜到三个仓库，描述几乎逐字对应本题：

- `EgonKenai/unity-ar-inspection` ★0
- `Sunly9/ar-inspection` ★0（描述里带「无 AR 设备备选版」）
- `zlb0401/unity-ar-inspection-go-react` ★0

**判断：不参考其代码，连看也不看。**

理由三条：

1. 这是面试作业，评审要看 `AI_LOG.md` 和"能否解释核心代码"，抄来的东西在题目第 8 条第 4 项直接丢分；
2. 这三个仓库全是 ★0、无任何质量信号，可能是半成品或 AI 直出；
3. 结构上这类项目骨架就是「三端 + 一个 JSON schema」，我们自己设计不会更差。

## 三、落到我们身上的三条结论

1. **AR 那 4 个动作不用自己发明**：照官方 `SimpleAR` 的 `ARRaycastManager` 用法写，再加平面可视化 + 表单。
2. **业务字段用 CMMS 对照一遍**：重点检查 assignedTo（派给谁）、dueDate（承诺完成时间）、closedBy（谁关的）是否值得进 v1。
3. **跨会话定位留到加分项**：`Markers`（图像追踪）是唯一成本可接受的方向，云锚点不做。
