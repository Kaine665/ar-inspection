# 开发版本一：仅完成业务逻辑版

> 这一版只谈业务。代码、框架、语言一律不出现。

## 0. 一句话定义

> 让「现场看见的问题」变成一条**能被追踪到关闭**的记录。
> AR 只是把「位置」这一项填得比嘴描述更准的手段，不是目的。

## 1. 业务目标与成功标准

**用户视角**

- 巡检员：从看到问题到提交完成，**90 秒内**，不需要培训。
- 管理员：打开电脑**5 秒内**知道今天要处理什么、哪个最急。

**业务视角**

- 一条记录从上报到关闭，全过程**状态可查、位置可描述、时间可追溯**。

**v1 明确不做**：账号与权限、实时推送、跨会话定位、统计报表、消息通知。

## 2. 角色

| 角色 | 在哪 | 用什么 | 手上的约束 | 他要的是 |
|---|---|---|---|---|
| **巡检员** | 现场（地下车库、楼顶、配电间） | 手机 | 站着、可能戴手套、照明差、可能没信号、不想学新东西 | 三步报完，别让我填 10 个字段 |
| **管理员** | 办公室 | 电脑 | 一堆待办、被领导问、要交代"处理到哪了" | 一眼看出哪个急、改一下状态就完事 |
| **维修工（不进系统）** | 现场 | 嘴和手 | 拿到的可能是别人转述的一句话 | 一条能看懂的问题 + 一张能找到地方的图 |

第三个角色虽然不登录系统，但他决定了系统必须存什么：**截图和文字描述**。这两个字段是为他准备的，不是为管理员。

## 3. 业务对象：一条「问题」

**一条问题 ≠ 一个标记。** 标记是空间表达（几何），问题是业务实体（有主、有状态、有结果）。

业务定义：

> **某个时刻，某个人，在某个位置，观察到的一件需要有人处理的现场缺陷。**

由此推出两条边界：

- **没有位置，仍然是一条问题**（人可以靠描述和图片找到它）。
- **没有标题，就不成其为问题**（无法转述、无法列在清单上、无法派单）。

这两条是后面所有规则的根。

## 4. 正向流程：标准一天

**A · 主流程（标准一天）**
张师傅巡检 → 发现裂缝 → 扫描地面 → 放标记 → 标题「B1 入口墙面破损」+ 描述 + 优先级高 → 提交 → 管理员当天看到 → 派单，改「处理中」→ 次日报「已解决」。

## 5. 业务规则（编号，可逐条验证）

| 编号 | 规则 | 为什么（业务理由） |
|---|---|---|
| **BR-01** | 上报最小集：标题必填、描述可选、优先级三选一（默认「中」） | 少于这个，管理员无法判断 |
| **BR-02** | 标题要写「位置 + 现象」，不是「坏了个东西」 | 标题是**唯一会被转述**的字段，维修工只听到标题 |
| **BR-03** | 优先级 = 响应承诺：高=当天到场、中=本周、低=排期 | 三档如果不承诺时间，就只是装饰 |
| **BR-04** | 位置必须**双轨**：坐标（给机器）+ 一句话（给人："入口左侧墙面，距地约 50 cm"） | 只有坐标 = 机器能懂人不懂；只有文字 = 人懂机器不懂 |
| **BR-05** | 位置是**快照**，不是地址：只属于本次现场，必须配一张现场截图 | 换人、重启、换角度都不复现（这就是那条题目的减负） |
| **BR-06** | 巡检员只能**新建**，不能改；状态只能由管理员改 | 现场改状态 = 自己给自己结案 |
| **BR-07** | 状态只能单向前进；**已解决可以被重开** | 裂缝会复发，一次修复不等于永久 |
| **BR-08** | 每次改状态必须留痕（何时、从什么到什么） | 被问"什么时候改的"时必须答得出 |
| **BR-09** | 提交失败必须可见 + 可重试 + 不丢已填内容 | 现场网络差是常态，不是异常 |
| **BR-10** | 记录**永不物理删除**，作废是状态 | 审计；删了就没有"这里曾经出过问题"的历史 |
| **BR-11** | 同一区域短时间多条，先当**独立问题**存，由人判断是否重复 | 自动合并会错，重复上报的代价低于误合并 |
| **BR-12** | 记录的创建时间 = **上报时刻**，不等于发现时刻 | 现场可能先记下来、晚上回办公室才报。v1 接受这个偏差并声明 |

## 6. 状态机（业务语义）

| 状态 | 业务含义 | 谁能改到这里 | 依据 | 下一步 |
|---|---|---|---|---|
| **待处理** | 已登记，还没人负责 | 巡检员上报（系统生成） | 提交成功 | 管理员分诊 → 处理中 |
| **处理中** | 有人接了，正在干 | 管理员 | 派人 / 已到现场 | 干完 → 已解决 |
| **已解决** | 现场修好了 | 管理员（或授权维修方） | 有结果说明/照片 | 复发 → 回待处理 |

**题目只要求这三态。业务上真实存在第四、第五态**：作废（误报/重复）、已验收（管理员确认修复质量）。v1 把它们折叠进「已解决 + 描述」，并在 README 声明——这就是"未完成内容如实说明"的写法。

## 7. 每个字段的业务解释

| 字段 | 谁填 | 业务用途 | 缺了会怎样 |
|---|---|---|---|
| 标题 | 巡检员 | 唯一被转述、被列表展示的字段 | 管理员看不懂清单 |
| 描述 | 巡检员（可空） | 补充细节，判断严重程度 | 影响分诊精度，不影响流程 |
| 优先级 | 巡检员初判 | 响应承诺，决定排序 | 所有问题一样急 = 没有优先级 |
| 状态 | 系统 + 管理员 | 追踪处理进度 | 无法回答"处理到哪了" |
| 位置坐标 | 手机自动 | 现场当时的空间记录，供对照 | BR-05 说明：单独存在时价值有限 |
| 位置文字 | 巡检员 | 人找位置的真正依据 | 坐标变孤岛 |
| 现场截图 | 手机自动 | 维修工与核验者"认位置、认问题" | 跨人交接失效 |
| 创建/更新时间 | 系统 | 算闭环时长、追责 | 无法度量这套系统是否有用 |

## 8. 什么算「闭环」

一条问题真正结案，业务上要三件事同时成立：

1. **状态 = 已解决**
2. **有人签名**（谁修的 / 谁确认的）
3. **有结果证据**（维修后照片或说明）

v1 只保证第 1 条 + 时间戳。第 2、3 条是"已知缺口"，而且这个缺口说清楚，比塞一个假签字更有分。

## 9. 岔路与例外

**B · 无网络（地下车库常态）**
张师傅填完点提交 → 转圈 → 失败提示「当前无网络，已保留填写内容」→ 他走出来到有信号的地方 → 重试 → 成功。
**要点：失败不能吞掉他填的东西。** 现场人员最不能接受的是"白填一遍"。

**C · 检测不到平面（白色环氧地坪 + 强反光）**
他对着地面晃了 20 秒，网格始终不出现。他需要一句人话：「请缓慢移动手机，对准有纹理的地面」+ 一个出口。
**业务上的真相**：真实系统一定会给他一个"我先拍照+写文字，位置稍后补"的降级通道。**v1 不做**（题目要求位置来自标记），但要写进已知问题。如果不写，等于假装现场不会发生这件事。

### 其余例外与兜底（业务口径，不是技术口径）

| 情况 | 业务处理 |
|---|---|
| 现场无网络 | 提示 + 保留内容 + 可重试（BR-09） |
| 检测不到平面 | 引导话术 + 明确出口；v1 无降级通道，记入已知问题 |
| 同一问题被两人报 | 先当两条独立记录，管理员人工判重（BR-11） |
| 误报 | 本应作废；v1 走「已解决 + 描述：误报」并声明 |
| 报了以后现场自己好了 | 走「已解决」，无需修 |
| 手机不支持 AR | 换设备或换人报；这类问题不该发生，兜底 = 人工转述 |
| 记录很久没人动 | 业务上这是管理问题，不是系统问题——但"open 积压数"要算得出来 |

## 10. 怎么判断这套业务是有效的

如果这是真产品，看四个数：

1. **平均闭环时长**（上报 → 已解决）
2. **重复上报率**（同一位置在 24 小时内报了几次）
3. **误报率**（已解决里"误报"占多少）
4. **open 积压数**（超过 3 天还待处理的）

v1 不算这些，但**数据结构必须让它们算得出来**——这直接决定了字段一个都不能少。

## 11. v1 边界

| 做 | 不做（写进已知问题） |
|---|---|
| 三态流转 + 更新时间戳 | 作废 / 验收 / 签名 |
| 标题 + 描述 + 优先级 + 坐标 + 文字位置 | 截图上传（强烈建议做，成本极低） |
| 失败提示与重试 | 离线暂存 |
| 列表 + 状态修改 | 筛选、排序、搜索、删除 |
| 后端重启数据仍在 | 登录、权限、通知 |

## 12. 需要你拍板的四个业务决策

1. **「已解决」谁确认？** 巡检员回访确认 / 管理员一句话 / 无需确认。我的建议：v1 = 管理员一句话，README 写"缺验收环节"。
2. **优先级能不能被管理员改？** 我的建议：v1 不能改（题目只要求改状态），但要意识到这是缺口——真实系统里管理员一定会重排。
3. **要不要做截图？** 我的建议：**做**。它补的正是 BR-05 那个洞，成本不到一小时，业务价值最高。
4. **作废状态 v1 做不做？** 我的建议：不做，写进已知问题。多一个状态就要多一套 UI 和校验，而演示里不加分。
