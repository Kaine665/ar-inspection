# 方法记录

## 一、检查点

| 位置 | 问什么 |
|---|---|
| 前置 | 进来之前必须成立的条件是什么？不成立时用户看到什么？ |
| 主操作 | 核心动作成功的判据是什么？这个成功，用户自己能不能独立确认？ |
| 失败路径 | 每一步可能以什么方式失败？失败后用户能不能自己恢复？ |
| 事后 | 动作完成后，状态能不能被下一步验证？ |

## 二、评估点

| 标准 | 问什么 | 取向 |
|---|---|---|
| 暴露时机 | 这个点错了，什么时候会发现？当场 → 演示时 → 上线三个月 → 永远不暴露 | 越晚暴露越值得写下来 |
| 沉默性 | 错了会不会响？崩溃会响，坐标漂移不会响 | 沉默的优先 |
| 跨端性 | 这个点涉及几个端、几次交互？（手机 → 后端 → 网页） | 越多越容易"以为约好了，其实没约"，优先 |

## 三、顺序

写一条链路按这个顺序，不能跳：

1. **先写逻辑**：把链路拆成步骤，每步写清前置条件、成功判据、变坏时用户看到什么。
2. **再定检查点**：检查点挂在步骤边界上。没有步骤，检查点只能凭感觉挑；有了步骤，"前置 / 主操作 / 失败路径 / 事后"四个位置才有落脚点。
3. **最后落断言**：每个检查点 1–3 条可判真假的事实；状态只对断言标，不对检查点标。

**必须分清两类东西：**

- **步骤**是线性的，沿时间往下走（相机就绪 → 会话就绪 → 平面检测 → 放置 → 停留）。
- **贯穿条件**不属于任何一步，它对所有步骤同时成立或不成立（跟踪质量就是这一类）。

把贯穿条件当成一个步骤来写，门控就会挂在错的地方。正确的形态是二维表：横轴是步骤，纵轴是贯穿条件的档位，每个格子都是一个检查点候选。

## 四、断言写法

**四格模板**：在【条件】下，【可观察的东西】出现/变成【判据】，误差/时限【边界】。

| 格 | 含义 |
|---|---|
| 条件 | 什么情形下——尽量落到状态量（跟踪档位、HTTP 状态、有无平面） |
| 可观察物 | 屏幕上的像素、库里的行数、响应里的字段、两个坐标的距离——不许是"系统行为"这种抽象名词 |
| 判据 | 成立/不成立的界线（有/无、等于、≤、包含某句文案） |
| 边界 | 容差、时限、什么不算 |

**四步操作**

1. 把检查点拆成"是/否"：一个检查点通常含着两三个独立的是非题，先数出来。
2. 每道是非题写一句，主语换成可观察量。
3. 补边界：多准、多久、哪种情况不算。
4. 三把尺子自检：
   - 一次操作能给出真假吗？（要长期观察 → 不成立）
   - 判据里有实现细节吗？（有 → 那是口径，得单列）
   - 判 ❌ 时知道去哪一层改吗？（不知道 → 再具体一点）
